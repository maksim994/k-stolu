# Развёртывание «К столу» в Coolify

Инструкция для уже установленного Coolify и одного домашнего сервера. На сервере запускаются два контейнера: приложение и PostgreSQL 17. Рецепты, подборки и встроенные фотографии входят в репозиторий. Node.js на сервер устанавливать не нужно: сборка происходит в Docker. На Mac для генерации настроек нужен Node.js 22.

## 1. Доступ к репозиторию

Используйте закрытый GitHub-репозиторий [maksim994/k-stolu](https://github.com/maksim994/k-stolu), ветку `main`.

В Coolify подключите GitHub App через **Sources**, установите её в свой GitHub-аккаунт и разрешите доступ только к этому репозиторию. Альтернатива: **Private Repository (with deploy key)** и отдельный read-only SSH-ключ. Не передавайте Coolify личный пароль GitHub.

Репозиторий повторно создавать не нужно. Для дальнейших отправок с этого Mac используется уже настроенный SSH-доступ. Coolify получает собственный read-only доступ к репозиторию через GitHub App или deploy key, а не SSH-ключ этого компьютера.

## 2. Домен и домашняя сеть

Выберите постоянный адрес, например `https://recipes.example.ru`. Для обычного публичного HTTPS домен должен указывать на домашний сервер, а входящие TCP 80/443 — попадать на прокси Coolify. Не публикуйте наружу PostgreSQL, порт приложения 3000 и панель администрирования Coolify.

При CGNAT одного проброса портов недостаточно: сначала потребуется подходящий туннель, VPN или внешний прокси. Для доступа только из дома/VPN настройте внутренний DNS и доверенный HTTPS. Эти сетевые настройки зависят от вашего сервера и провайдера и не выполняются самим проектом. Если сайт доступен из интернета, каталог рецептов будет публичным; пароль защищает только `/admin`.

## 3. Отдельные серверные секреты

На Mac в папке проекта выполните, заменив пример своим настоящим адресом:

```sh
npm run setup:production -- https://recipes.example.ru
```

Команда создаёт:

- `.local/coolify.env` — настройки для Coolify;
- `.local/coolify-admin-password.txt` — новый пароль админки.

Локальные `.env` и пароль не меняются. Серверные файлы исключены из Git и Docker-образа, доступны только владельцу и не перезаписываются повторным запуском. Сохраните секреты в менеджере паролей. Не отправляйте их в чат и не добавляйте в репозиторий. После переноса в Coolify держать эти файлы на сервере не требуется.

В **Environment Variables** приложения Coolify внесите значения из `.local/coolify.env`. Они нужны во время выполнения, а не сборки; выключите передачу секретов в build. В Developer view не удаляйте уже существующие служебные переменные Coolify при добавлении этих шести значений.

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_USER` | `cooking` |
| `POSTGRES_DB` | `cooking` |
| `POSTGRES_PASSWORD` | Сгенерированный пароль базы в hex-формате |
| `ADMIN_PASSWORD_HASH` | Полная строка `scrypt:…:…`, не пароль в открытом виде |
| `SESSION_SECRET` | Сгенерированный секрет сессий |
| `APP_ORIGIN` | Реальный адрес сайта, например `https://recipes.example.ru`, без пути и завершающего `/` |

`DATABASE_URL` вручную не задавайте: Compose собирает его для внутреннего сервиса `db`. Hex-пароль безопасен внутри URL без дополнительного кодирования. Генератор сразу создаёт такие пароли.

Не запускайте генератор при каждом обновлении. Изменение `POSTGRES_PASSWORD` в Coolify **не меняет пароль в уже созданной базе** и приведёт к ошибке подключения. Смена пароля базы требует отдельной согласованной операции. Смена `SESSION_SECRET` завершает все администраторские сессии.

## 4. Создание приложения

В нужном проекте Coolify: **New Resource → Private Repository (with GitHub App)**, выберите репозиторий и домашний сервер. Названия пунктов могут отличаться в установленной версии.

| Настройка | Значение |
| --- | --- |
| Branch | `main` |
| Build Pack / Build strategy | `Docker Compose` / `Compose` |
| Base Directory | `/` |
| Docker Compose Location | `/compose.yaml` |
| Raw Compose | выключено; доменами управляет Coolify |
| Auto Deploy | сначала выключено / Manual deployments only |

Сохраните и загрузите Compose-конфигурацию. Не выбирайте **Docker Compose Empty**: этот ресурс не связан с Git и не получает будущие изменения проекта. Не подключайте `compose.local.yaml`: он нужен только для localhost на Mac. Не задавайте свои Build/Start commands: Dockerfile уже содержит сборку, а запуск выполняет миграции перед приложением.

В доменах выберите сервис **app** и укажите `https://recipes.example.ru:3000`. Здесь `:3000` обозначает внутренний порт контейнера для прокси Coolify. В браузере адрес будет **без `:3000`**, и `APP_ORIGIN` тоже должен быть без этого внутреннего порта. Сервису **db** домен и публичный порт не нужны.

В Persistent Storage проверьте два отдельных тома:

- `postgres_data` → `/var/lib/postgresql/data`;
- `uploads` → `/app/uploads`.

Coolify управляет фактическими именами томов. Не меняйте их после установки и не удаляйте ресурс ради обычного обновления. Права пользовательских изображений — UID/GID `1001:1001`. Встроенные фотографии лежат в образе, а не в uploads.

Compose уже задаёт проверки готовности и ограничение размера логов. Healthcheck приложения проверяет подключение к базе и завершение синхронизации начального каталога.

## 5. Первый запуск

Нажмите **Deploy**, дождитесь сборки и здорового состояния обоих сервисов. В логах приложения должны появиться `Миграции применены.` и `Catalog seed sync:`. Первый запуск создаёт каталог из репозитория: сейчас это 121 рецепт, 91 продукт и 35 подборок. Все встроенные фотографии входят в сборку.

Проверьте:

1. `https://ваш-домен/api/health` возвращает `{"status":"ok"}`.
2. Каталог, подборки и несколько рецептов открываются с фотографиями.
3. Вход в `/admin` работает с новым серверным паролем.
4. Создайте отдельный тестовый черновик, загрузите фото и сохраните. Черновик не должен появиться в публичном каталоге.
5. Выполните повторный Deploy и проверьте, что черновик и фото остались.
6. Сделайте резервную копию и проверьте восстановление в отдельной тестовой установке.

Без переноса базы будут доступны рецепты из кода, но не локальные изменения, сделанные через админку. Для переноса такого контента экспортируйте JSON из локальной админки и импортируйте его на сервере. Экспорт не включает файлы `/media/...`: их нужно перенести отдельно вместе с uploads или загрузить заново. Полный перенос базы и uploads тоже возможен через резервную копию ниже; секреты окружения при этом не переносятся автоматически.

## 6. Будущие рецепты и изменения

Рабочий процесс остаётся прежним: добавляем рецепты, подборки и изображения в этот локальный проект, проверяем, делаем коммит и отправляем его в `main`. На сервере не нужно вручную создавать те же блюда. После успешного GitHub Actions **Checks** нажмите Deploy в существующем приложении Coolify и убедитесь, что выбран нужный коммит.

```sh
npm ci
npm run format:check
npm run typecheck
npm test
npm run build
git add .
git diff --cached --stat
git commit -m "Add recipes and collections"
git push origin main
```

В репозитории уже есть CI с тестами, проверкой типов, форматирования и production-сборкой. Для тестов обновления контента CI использует отдельный PostgreSQL, а не вашу рабочую базу.

Правила синхронизации при запуске новой версии:

- Новые ID автоматически добавляются в базу.
- Изменения существующих рецептов, продуктов и подборок из кода применяются, если запись не менялась относительно предыдущей отслеживаемой версии.
- Правки из админки, импортированные отличающиеся записи и архивные статусы сохраняются. Обновление не перезаписывает их молча.
- Для старой базы без истории сравнения отслеживание начинается только с записей, полностью совпадающих с текущим кодом. Остальные остаются как есть.
- Удаление рецепта из исходников само по себе не удаляет запись с сервера. Для снятия с публикации используйте архив в админке или отдельную согласованную миграцию.

История хранится в таблице `seed_snapshots`. В логах синхронизации показываются количества добавленных, обновлённых и сохранённых записей. Если рецепт намеренно изменён на сервере, но нужна именно новая версия из кода, сначала экспортируйте текущий каталог, затем импортируйте согласованный JSON с тем же ID. Импорт — явное обновление; оно заменяет переданные записи целиком. Не переименовывайте ID ради исправления рецепта: это создаст дубликаты и нарушит ссылки из личных списков.

**Источник редакторских правок нужно согласовать:** изменения через серверную админку не попадают обратно в Git. Перед работой над таким рецептом экспортируйте его актуальную версию и перенесите нужные изменения в исходники. Это позволяет сохранить серверную редактуру и продолжать обновления из репозитория.

Можно позже включить Deploy on push через GitHub App. Такой webhook сам по себе не ждёт CI; сначала оставьте ручной Deploy после зелёных проверок. Автодеплой только после CI можно подключить отдельным workflow, когда сервер будет доступен. Сейчас внешние webhook и токены не настроены.

Обычное обновление не удаляет тома. **Никогда не выполняйте `docker compose down -v` и не удаляйте volumes для обновления.** Не подключайте тестовые/preview-установки к рабочим томам.

## 7. Резервная копия

Нужны три независимые части: PostgreSQL, uploads, секреты из Coolify. Git хранит исходники и встроенные фото, но не заменяет резервную копию базы. Личные списки браузера в серверную копию не входят.

На сервере по SSH найдите точные имена контейнеров этого ресурса в Coolify или через `docker ps`. Не используйте локальные имена `k-stolu-app-1` наугад — Coolify назначает свои.

Скрипт находится в репозитории `scripts/backup.sh`. Его можно отдельно перенести с Mac на сервер через `scp`/SFTP; клонировать весь проект ради резервного копирования не обязательно. Ниже команда из копии репозитория на сервере; если перенесли только скрипт, замените `scripts/backup.sh` его путём:

```sh
sh scripts/backup.sh ИМЯ_КОНТЕЙНЕРА_DB ИМЯ_КОНТЕЙНЕРА_APP /защищённый/путь/backup-2026-10-12
```

Каталог назначения должен быть новым. Скрипт создаёт `catalog.dump`, `uploads.tar.gz` и `image-id.txt`, проверяет читаемость архивов и не выводит секреты. Он требует только shell и Docker, не Node.js. Незавершённые файлы имеют суффикс `.partial` и не считаются готовой копией. На время копирования не редактируйте каталог и не загружайте изображения. Запишите также Git SHA текущего успешного развёртывания из Coolify: локальный Docker image ID не заменяет версию в Git.

Держите хотя бы одну копию **вне домашнего сервера**, а секреты — в менеджере паролей. Делайте копию перед обновлениями и регулярно по расписанию выбранным способом. Само расписание этим проектом не включается.

## 8. Восстановление и откат

Сначала проверьте восстановление в отдельном ресурсе с отдельными томами, тем же Git-коммитом и PostgreSQL 17. Для рабочего восстановления приостановите автодеплой, закройте доступ посетителям и сделайте резервную копию текущего состояния.

Следующие команды **заменяют содержимое выбранной базы**. Внимательно проверьте DB/APP и абсолютный путь BACKUP. Выполняются по SSH на сервере, не в терминале контейнера.

```sh
DB='точное-имя-контейнера-db'
APP='точное-имя-контейнера-app'
BACKUP='/абсолютный/путь/к/готовой/копии'

docker exec -i "$DB" pg_restore --list < "$BACKUP/catalog.dump"
docker exec -i "$APP" tar -tzf - < "$BACKUP/uploads.tar.gz"
IMAGE=$(docker inspect --format '{{.Config.Image}}' "$APP")
docker stop "$APP"
docker exec -i "$DB" sh -c 'exec pg_restore --exit-on-error --single-transaction --clean --if-exists --no-owner --no-acl -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < "$BACKUP/catalog.dump"
docker run --rm --user 0 --volumes-from "$APP" --mount "type=bind,src=$BACKUP,dst=/backup,readonly" --entrypoint sh "$IMAGE" -c 'tar -xzf /backup/uploads.tar.gz -C /app/uploads && chown -R 1001:1001 /app/uploads'
docker start "$APP"
```

Выполняйте команды по одной. При любой ошибке **не переходите к следующей команде**. После остановки приложения том остаётся доступен вспомогательному контейнеру. Восстановление uploads не удаляет посторонние файлы, но возвращает файлы из копии; для точного полного восстановления используйте новый пустой том. После запуска миграции применяются автоматически. Проверьте `/api/health`, количество рецептов, вход в админку и открытие пользовательских фотографий.

Откат приложения: разворачивайте предыдущий проверенный Git-коммит в **том же** ресурсе Coolify, сохраняя тома. Это не откат базы: новые SQL-миграции не отменяются, новые рецепты не удаляются, редакторские правки сохраняются. Автоматически отслеживаемый неизменённый контент может вернуться к версии выбранного коммита. Для полного возврата данных нужна соответствующая резервная копия. Будущие SQL-миграции делайте совместимыми с предыдущей версией приложения либо заранее планируйте восстановление и окно обслуживания. Не меняйте major-версию PostgreSQL как обычное обновление образа.

## 9. Что хранится в браузере

Избранное, продукты дома, покупки и план питания пока находятся в `localStorage` конкретного браузера. Они сохраняются при обновлении сайта на том же домене, но не синхронизируются между устройствами. Переезд с `localhost:3037` на новый домен **не перенесёт их автоматически**. Смена HTTP на HTTPS тоже меняет хранилище. Кнопки пользовательского экспорта/импорта пока нет; при необходимости отдельный перенос этих списков нужно сделать до очистки старого браузера. Серверная админка и экспорт каталога не являются копией этих данных.

## 10. Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Сайт не открывается / 502 | DNS, доступность прокси, домен выбран для app, внутренний порт 3000, состояние обоих контейнеров |
| Вход или сохранение отклоняются | `APP_ORIGIN` точно совпадает с адресом в браузере; без внутреннего `:3000`, другого домена, пути или старого localhost |
| Ошибка пароля PostgreSQL | Не менялся ли пароль окружения после создания тома; содержимое старой базы не переинициализируется |
| Фото не загружается | uploads смонтирован в `/app/uploads`, права `1001:1001`, свободное место, лимит загрузки в прокси |
| Новые рецепты не появились | Развёрнут ли свежий коммит main, прошла ли синхронизация; существующая серверная правка может быть сохранена намеренно |
| После пересоздания всё пусто | Проверить, не выбран ли другой ресурс или новые тома; не удалять старые до восстановления |
