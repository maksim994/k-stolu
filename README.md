# К столу

Семейная книга рецептов: сначала выбираем блюдо, затем уточняем продукты, технику и время. Каталог содержит 121 рецепт: 25 завтраков, 27 салатов, 24 перекуса и по 15 супов, вторых блюд и выпечки, 150 способов приготовления и 35 подборок. Каталог открыт, управление защищено паролем. Личные продукты, избранное и покупки сохраняются в браузере отдельно на каждом устройстве.

Новая рубрика: [8 перекусов](docs/snack-batch.md), три подборки и отдельный приём пищи «Перекус» в плане.

Продолжение: [ещё 8 перекусов](docs/snack-batch-02.md), подборки «Сладкие перекусы» и «Перекусы на общий стол».

Третья партия: [8 перекусов для контейнера и заморозки](docs/snack-batch-03.md), две новые подборки и отдельный способ приготовления мини-котлет в аэрогриле.

Новая партия: [12 салатов для ужина и общего стола](docs/salad-batch-02.md), включая три тёплых салата и отдельный способ приготовления курицы в аэрогриле.

## Запуск в Docker

Нужны Docker Compose и Node.js 22 для первого создания настроек.

```sh
npm run setup
docker compose -f compose.yaml -f compose.local.yaml up -d --build
```

Приложение: http://localhost:3037. Админка: http://localhost:3037/admin. Сгенерированный пароль находится в `.local/admin-password.txt`. Настройки и секреты — в `.env`; оба файла исключены из Git и Docker-образа. При повторном `setup` существующие настройки сохраняются.

```sh
docker compose -f compose.yaml -f compose.local.yaml logs --tail=50 app
docker compose -f compose.yaml -f compose.local.yaml stop
```

Остановка и пересборка сохраняют базу и загруженные изображения в volumes. `down -v` удалит их, поэтому для обычного обновления используйте `up -d --build`.

## Разработка

```sh
npm ci
npm run setup
docker compose -f compose.yaml -f compose.local.yaml up -d db
npm run db:migrate
npm run dev -- --port 3037
```

Перед запуском dev остановите Docker-сервис `app`, если он занимает порт. Локальный PostgreSQL доступен только на `127.0.0.1:55438`. Домен и протокол должны совпадать с `APP_ORIGIN`: это важно для входа и сохранения через админку.

```sh
npm test
npm run typecheck
npm run build
node scripts/verify-browser.mjs
node --env-file=.env scripts/verify-storage.mjs
node scripts/verify-plan.mjs
node --env-file=.env scripts/verify-api.mjs
node --env-file=.env scripts/verify-wellness.mjs
node --env-file=.env scripts/verify-collections.mjs
```

Браузерная проверка использует установленный Google Chrome. Интеграционные проверки предназначены для локальной тестовой среды: API-проверка создаёт временный рецепт, проверяет публикацию и архив, затем удаляет только его. Снимки экрана находятся в `.local/qa`. `npm run format` форматирует исходники.

## Coolify на домашнем сервере

Подробная пошаговая инструкция: [развёртывание, обновления, резервные копии и восстановление](docs/coolify.md).

Для отдельной генерации серверных секретов, не затрагивая локальный запуск:

```sh
npm run setup:production -- https://recipes.example.ru
```

Настройки появятся в `.local/coolify.env`, пароль — в `.local/coolify-admin-password.txt`. Замените пример своим настоящим HTTPS-адресом. Репозиторий содержит GitHub Actions Checks; сначала рекомендуется ручное развёртывание после успешных проверок.

1. Подключить этот проект как Git-based Docker Compose Application; файл Compose — `compose.yaml`. Локальное дополнение `compose.local.yaml` на сервере не подключать.
2. Задать runtime-переменные `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`, `ADMIN_PASSWORD_HASH`, `SESSION_SECRET`, `APP_ORIGIN` из `.local/coolify.env`. Пароль базы оставить в сгенерированном hex-формате: он корректен внутри URL подключения. `DATABASE_URL` Compose формирует автоматически.
3. Привязать HTTPS-домен к сервису `app`, внутренний порт `3000`. В `APP_ORIGIN` записать публичный адрес без завершающего `/`, например `https://recipes.example.ru`. Внешний доступ к PostgreSQL не требуется.
4. Развернуть и проверить `/api/health`, каталог, вход в админку, сохранение рецепта и загрузку изображения.
5. Настроить резервные копии базы и volume `uploads`, проверить восстановление. Перенос текущей локальной базы нужен только при желании сохранить внесённые изменения: свежая установка сама добавит стартовые рецепты.

Compose содержит зависимости, health checks, persistent volumes и запуск миграций до приложения. База ждёт готовности, а начальный каталог синхронизируется по стабильным ID: новые записи добавляются, неизменённые стартовые записи обновляются, редакторские правки сохраняются. История версий начального контента хранится в `seed_snapshots`. Старые отличающиеся записи без истории не перезаписываются. Удаление из исходников не удаляет данные базы; снятие с публикации делается архивированием.

Источники по настройке: [Docker Compose в Coolify](https://coolify.io/docs/applications/builds/docker-compose), [переменные окружения](https://coolify.io/docs/applications/configuration/environment-variables), [домены](https://coolify.io/docs/core/networking/domains). Фактическое развёртывание на домашнем сервере пока не выполнялось.

## Контент и админка

Подборки доступны во вкладке каталога `/?view=collections`; на телефоне в обычном каталоге — через значок книг справа от заголовка. В админке раздел «Подборки» позволяет создать ручной список, изменить порядок рецептов или настроить автоматические правила по категории, семейству блюд, технике, общему времени и заморозке. Все условия применяются к одному способу приготовления. Закреплённые рецепты поднимаются выше только при соответствии правилам; черновики и архив не показываются. JSON версии 1 дополнен необязательным массивом `collections`: старый импорт без него не удаляет существующие подборки.

Внизу рецепта блок «Попробуйте ещё» предлагает до трёх опубликованных блюд, приоритет — тому же семейству, затем категории и общим продуктам. Поля `family` и `tested` редактируются у рецепта. [Первая партия завтраков](docs/breakfast-batch-01.md), [вторая партия завтраков](docs/breakfast-batch-02.md), [первая партия супов](docs/soup-batch-01.md), [первая партия вторых блюд](docs/main-batch-01.md), [первая партия салатов](docs/salad-batch-01.md) и [первая партия выпечки](docs/baking-batch-01.md) содержат сведения о составе партий, источниках ориентиров и сгенерированных иллюстрациях. Обновление стартового контента не перезаписывает редакторские изменения. Серверные правки из админки не попадают в Git автоматически: перед совместным редактированием их нужно экспортировать и согласовать с исходниками.

Редактор позволяет менять название, категорию, описание, фото, статус, состав и шаги каждого способа приготовления. Черновики и архив скрыты из публичного каталога. Есть предпросмотр, импорт и экспорт JSON версии 1. Импорт обновляет записи по ID и не удаляет отсутствующие записи; весь пакет проверяется до записи в транзакции. Новые продукты можно добавить через импорт: для первой версии отдельный редактор справочника не сделан.

В рецепте есть блок «Хранение»: примерный срок в холодильнике, возможность заморозки и примечание. В редакторе срок можно оставить пустым, а заморозку — «Не указано». JSON версии 1 поддерживает необязательный объект `storage`: `fridgeDays` (целое число от 1 до 30 или `null`), `freezable` (`true`, `false` или `null`), `note` (до 1000 символов). Старые файлы без этого объекта импортируются как раньше. При запуске сведения добавляются только к неизменённым стартовым рецептам; редакторские изменения сохраняются.

Сроки стартовых блюд — консервативные ориентиры после приготовления при температуре не выше +4 °C и помещении в холодильник в течение 2 часов, а не гарантия свежести. Основа: [FoodSafety.gov — хранение в холодильнике и морозильнике](https://www.foodsafety.gov/food-safety-charts/cold-food-storage-charts), [быстрое охлаждение готовой еды](https://www.foodsafety.gov/blog/10-smart-tips-keep-your-restaurant-leftovers-safe). Примечания о текстуре после заморозки опираются на [National Center for Home Food Preservation](https://nchfp.uga.edu/how/freeze/freeze-general-information/foods-that-do-not-freeze-well/); «Не рекомендуется» относится к качеству готового блюда.

`npm run admin:password` формирует хеш нового пароля для `ADMIN_PASSWORD_HASH`. После изменения переменной пересоздайте контейнер приложения. Для принудительного завершения существующих сессий смените также `SESSION_SECRET`.

Экспорт JSON сохраняет контент, но не бинарные изображения. Начальные фото входят в `public/images/recipes`; пользовательские — в volume `uploads`. Поэтому полный перенос требует и базы/JSON, и изображений.

Все стартовые рецепты и иллюстрации подготовлены с помощью ИИ; они не обозначены как проверенные семьёй. Шаги отдельно описаны для каждой техники. Время при смене порций не умножается автоматически: вместимость посуды и число партий зависят от устройства. Для ориентиров внутренней температуры использована [таблица FoodSafety.gov](https://www.foodsafety.gov/food-safety-charts/safe-minimum-internal-temperatures). После реальной готовки будем уточнять рецепты по семейным замечаниям.

Отметка «есть дома» обозначает наличие, а не остаток. Перед добавлением в покупки можно изменить выбранные продукты. Количества суммируются только в совместимых единицах: кг переводятся в г, л — в мл; ложки, штуки и масса остаются отдельными строками. Покупки фиксируют состав на момент добавления, поэтому последующее редактирование рецепта не изменит уже составленный список. Повторное добавление того же блюда обновляет его вклад.

Личные списки не синхронизируются и не входят в резервную копию сервера. Очистка данных браузера удаляет их; другой домен или протокол использует отдельное хранилище. Полный офлайн-режим пока не реализован.

## План питания

Раздел `/plan` показывает 3, 5 или 7 дней с выбранной даты. Блюдо можно добавить на завтрак, обед или ужин, выбрать способ приготовления и отдельно указать порции на приём пищи и размер готовящейся партии. Кнопка «В план» в рецепте открывает редактор с выбранным блюдом и способом.

Остатки привязываются к более раннему приготовлению. План проверяет доступные порции и порядок приёмов пищи; один запас нельзя распределить дважды. При удалении приготовления со связанными остатками запрашивается подтверждение. Это план распределения еды, а не фактический учёт приготовленного: наличие и свежесть нужно проверять самостоятельно. Для остатков отображается предупреждение, если планируемый день достигает примерного срока хранения или срок не задан.

«Собрать покупки» рассчитывает ингредиенты для всех приготовлений в видимом периоде по размеру партии; остатки повторно не учитываются. Обязательные недостающие продукты отмечены заранее, продукты дома можно включить вручную в предпросмотре. Необязательные ингредиенты не добавляются автоматически. После изменения плана нажмите «Обновить покупки»: состав обновляется по стабильным идентификаторам, без удвоения. Ручные покупки, отдельные добавления из рецептов и покупки для других периодов сохраняются. При неизменном составе сохраняются и отметки «куплено».

План хранится в том же локальном хранилище браузера, что избранное и покупки. Старые списки загружаются с пустым планом. Проверка `scripts/verify-plan.mjs` использует отдельный браузерный контекст и не меняет серверный каталог или личные списки открытого браузера. `src/domain/meal-plan.ts` содержит схему, расчёт порций остатков и сборку покупок.

## Резервная копия и восстановление

Для локального Compose:

```sh
mkdir -p .local/backups
docker compose -f compose.yaml -f compose.local.yaml exec -T db pg_dump -U cooking -d cooking -Fc > .local/backups/cooking.dump
docker compose -f compose.yaml -f compose.local.yaml exec -T app tar -C /app/uploads -czf - . > .local/backups/uploads.tar.gz
```

Имена пользователя и базы замените, если меняли их. Храните копии отдельно от сервера. Перед восстановлением сделайте свежую копию текущих данных и остановите `app`. Восстанавливайте в выбранную пустую базу через `pg_restore -U cooking -d cooking`, затем распакуйте архив изображений в `/app/uploads` с владельцем UID/GID `1001:1001`. Проверьте health, число рецептов и открытие изображений до включения общего доступа. Тест восстановления базы выполнен в отдельной временной базе, без изменения рабочей.

## Как развивать проект

| Модуль                         | Ответственность                                                |
| ------------------------------ | -------------------------------------------------------------- |
| `src/domain/recipe.ts`         | Типы, справочники, проверка структуры рецептов и импорта       |
| `src/domain/cooking.ts`        | Порции, выбор варианта, наличие продуктов, объединение покупок |
| `src/data/seed.ts`             | Стартовый контент, синхронизируемый без перезаписи редакторских правок |
| `src/server`                   | PostgreSQL/Drizzle, авторизация, ограничения запросов          |
| `src/app/api`                  | Публичный каталог, сессии, операции админки                    |
| `src/components/household.tsx` | Версионированное локальное хранилище личных списков            |
| `src/components`               | Экраны каталога, рецепта, продуктов, покупок и редактора       |
| `src/app/globals.css`          | Адаптивная визуальная система                                  |
| `migrations`                   | Версионированные SQL-миграции                                  |

Next.js/TypeScript обслуживает интерфейс и API, PostgreSQL хранит контент, Zod проверяет данные на границах. В первой версии рецепт с вложенными вариантами хранится целиком в JSONB, а ID, slug, статус и дата вынесены в столбцы. Это позволяет менять состав вариантов без разрастания миграций и сохранять рецепт атомарно. Справочник ингредиентов общий и связывается стабильными ID. При росте каталога индексы и нормализацию отдельных полей можно добавить миграцией без изменения экранов.

Новая техника затронет справочник, фильтр и контент; расчёты не зависят от конкретного устройства. Семейные ограничения добавим в модель рецепта и правила поиска. Для общей семейной корзины понадобится отдельная идентификация семьи и серверное хранилище личных данных — сейчас публичный посетитель не получает чужие списки.

Решения и исследование площадок: `PRODUCT.md`, `PLAN.md`. Выполненные этапы и следующий шаг: `PROGRESS.md`. Визуальные правила: `DESIGN.md`.
